# 🌭 Food for Thought: Processes

Chapter seven presented many scenarios and tools related to processes, which may all seem rather complicated at first.

However, the basic principle of processes is quite simple:

1. Processes are always started by or from another process.
2. Running processes are organised into a hierarchical tree based on their PIDs.
3. The first process is assigned PID 1, with subsequent processes being assigned ascending PIDs.

There is not much more to it than that.

## Background vs foreground

Commands can be executed (processes launched) either in the foreground or in the background.

If a command is run in the foreground, the session's input and output are reserved, meaning that no other commands can be executed in that session while the command is running.

When a command is run in the background, the input will be available for other tasks, but the command's output needs to be [redirected](08-redirections.md) to avoid disrupting the view.

## Process states

The most common process states are listed below:

| Code | State    | Meaning                                                                                     |
|------|----------|---------------------------------------------------------------------------------------------|
| `R`  | Running  | Executing on a CPU or waiting in the run queue for its turn.                                |
| `S`  | Sleeping | Waiting for an event (data, timer, user input). Wakes up by itself when the event occurs. Normal state for most processes. |
| `T`  | Stopped  | Suspended by a signal (`Ctrl+Z` / `SIGSTOP`). Frozen until explicitly continued with `SIGCONT` (`fg`/`bg`). |
| `Z`  | Zombie   | Already terminated, but the parent hasn't read its exit status yet. Only a process-table entry remains; cannot be killed. |

These can be observed in the `S/STAT` column of the `top` command, for instance.

::: note
Although zombie processes are not covered in our exercises, it is worth acknowledging them. These are processes that have already been terminated and inherited by the 'mother of all processes', PID 1, due to a missed exit by the parent.
:::

## Process priority

When a user starts a process by running a command, the process is assigned a priority level of `120`.

Processes can have priority levels ranging from 0 to 139, with _smaller_ values indicating a **higher** priority.

![Priority levels](imgs/priority_levels.png)

Priorities below `100` are considered real-time and are outside the scope of this course.

Users with admin access (`root`) can increase the priority by lowering the priority number all the way to `100`.

Users without admin access can only decrease the priority level by increasing the priority number up to `139`.

::: note
Note that the basic priority of `120` is marked with a value of `0`, as can be seen in the output of the `top` command. The root user can increase the priority by lowering the number by up to `-20`, whereas a standard user can decrease the priority by raising the number by up to `+19`.
:::
