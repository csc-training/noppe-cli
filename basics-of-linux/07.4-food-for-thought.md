# Food for Thought: Processes

Chapter seven presented many scenarios and tools related to processes, which may all seem rather complicated at first.

However, the basic principle of processes is quite simple:

1. Processes are always started by or from another process.
2. Running processes form a hierarchical tree.
3. The first process is assigned PID 1.

There is not much more to it than that.

## Background vs foreground

Commands can be executed (processes launched) either in the foreground or in the background.

If a command is run in the foreground, the session's input and output are reserved, meaning that no other commands can be executed in that session while the command is running.

When a command is run in the background, the input will be available for other tasks, but the command's output needs to be [redirected](08-redirections.md) to avoid disrupting the view.

## Process states

The most common process states are listed below:

| Code | State    | Meaning                                                                                     |
|------|----------|---------------------------------------------------------------------------------------------|
| `R`  | Running  | Executing on a CPU or waiting in the run queue for its turn.                                |
| `S`  | Sleeping | Waiting for an event (data, timer, user input). Wakes up by itself when the event occurs. Normal state for most processes. |
| `T`  | Stopped  | Suspended by a signal (`Ctrl+Z` / `SIGSTOP`). Frozen until explicitly continued with `SIGCONT` (`fg`/`bg`). |
| `Z`  | Zombie   | Already terminated, but the parent hasn't read its exit status yet. Only a process-table entry remains; cannot be killed. |

These can be observed in the `S/STAT` column of the `top` command, for instance.

::: note
Although zombie processes are not covered in our exercises, it is worth acknowledging them. These are processes that have already been terminated and inherited by the 'mother of all processes', PID 1, due to a missed exit by the parent.
:::

## Process priority

When a user executes a command, i.e. starts a process, the process is given a priority of `120`.

Linux ranks every process on a single internal priority scale from **0 to 139**, where a **lower number means a higher priority** (the process is given more CPU time when the system is busy). The scale is divided into three bands:

![Priority levels](/imgs/priority_levels.png)

- **Real-time (0&ndash;99)** — reserved for special real-time scheduling classes. Ordinary commands never run here; in `top` these appear as `rt` rather than a number.
- **Admin (100&ndash;120)** — to give a process a *better-than-default* priority, its `nice` value has to be pushed **below zero**. Only the root user (or a suitably privileged process) may do this, for example `sudo nice -n -5 mytask` to start one, or `sudo renice -n -5 -p PID` for a process that is already running.
- **User (120&ndash;139)** — the default landing spot for any command is **120**, i.e. a `nice` value of `0`. Any user is free to *raise* the nice value (`0` → `+19`), which *lowers* the priority. This is exactly what you did in the [running a process](07.2-running.md) chapter with `nice -n 10 sleep 1000 &` and `renice -n 9 -p PID`.

This is the theory promised back in 07.2: a normal user can only ever *increase* the nice value — moving to the right, toward lower priority. Moving *left* into the admin band, toward higher priority, requires elevated privileges.

::: note
The `top` command doesn't show the raw 0&ndash;139 kernel value. For normal processes it displays the 100&ndash;139 band as a `PR` column of `0`&ndash;`39` (where `PR = NI + 20`), next to the `NI` (nice) column running from `−20` to `+19`. That's why a process left at the default shows up as `PR 20`, `NI 0`.
:::
